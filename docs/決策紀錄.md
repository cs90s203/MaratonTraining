# 決策紀錄

規格審查（2026-09-10）留下的待決事項，在這裡定案。每一條都寫了「為什麼這樣選」與「反悔的成本」，
之後想改的時候不用重新推導一次。

---

## 0. 最高原則（使用者訂的，覆蓋以下所有細節）

> **休息或受傷的調整，不應該變相增加強度。**

這條不是感想，是可以拿來裁決設計的規則。它直接推翻三種常見做法：

| 常見做法 | 為什麼違反 | 本專案怎麼做 |
|---|---|---|
| 這週降量了，把少掉的量加到下週 | 把休息的代價往後推，等於沒休息 | 降量週**縮小分母**，少掉的量就是少掉了，不補 |
| 漏掉的課排進「補做清單」，累積起來 | 補做疊在既有課表上＝那天變成雙倍 | 補做只能**取代**當天原本的內容，不能疊加 |
| 中斷兩週回來，把剩下的週數壓縮 | 同樣的總量塞進更少的週＝強度上升 | 中斷就是往後順延，或直接接受計畫縮短 |

**驗收方式**：任何一個「調整」功能寫完之後，問一句「使用者用了這個功能，之後某一天的負荷會不會比原本高？」
會，就是做錯了。

## 1. 儲存後端 → **Firebase Auth + Firestore**

規格書原本寫「GitHub Contents API」，但那是 babylog **已經廢棄**的架構
（`~/Documents/Projects/babylog/docs/sync.md:4`：「已經整個換掉」）。廢棄理由（同檔 `:10`）：

> GitHub 版本每支手機都要手動申請、貼上一組 GitHub token 才能同步，對非工程背景的家人不友善。

而這個 App 的分享對象正是伴侶與教練。同一個坑不踩第二次。

**這個決定同時解掉四個問題**：blob sha 衝突、離線佇列、寫入權限強制、身分驗證。
Firestore 一天一筆文件（`users/{userId}/entries/{date}`）天生就是文件級併發，兩台裝置改不同天不會互相覆蓋。

**反悔成本**：低。Firebase 專案可以刪掉重來，資料量小。

## 2. 敏感健康資料的可見範圍 → **預設完全不分享**

`flags`（漏尿／疼痛／過度疲勞）與 `note`（自由文字身體狀況）**不進共享路徑**。
總覽頁看別人的完成度時，只讀 `status` 與時長的聚合結果，讀不到 flags。

Firestore 路徑分層：

```
users/{userId}/entries/{date}      ← 打勾 / 狀態 / 實際時長 / 距離 / actualNote（白名單內可讀）
users/{userId}/private/{date}      ← flags / note                            （只有本人可讀）
```

Security Rules 裡 `private/` 子集合綁 `request.auth.uid == userId`，不是靠前端不顯示。
babylog `docs/sync.md:23`：「真正的防線一定是 Security Rules，前端檢查只是體驗優化。」

**為什麼不問你**：分享是隨時可以打開的，收回來很難。預設關閉、之後想開再開。

> 第 13 條（2026-09-11）在 `entries` 加了一個共享的自由文字欄 `actualNote`（「實際做了什麼」），
> 那是使用者明確要的、給教練看的欄位，**不是**這條的例外——`private.note` 的邊界沒動。
> 兩個文字框在 UI 上並排，標題直接寫「誰看得到」，見第 13 條。

## 4. Week 23-26 的 28 天 → **從第四節進度表推導，並標記為推導值**

## 6. 強度以第二節對照表為準，不是模板的「心率/強度」欄

第一版把三張模板的「心率/強度」欄直接抄成資料，結果出現兩套互相矛盾的裁決：長跑用了
第二節的「長跑 65-72%」覆蓋模板，走跑交替卻照模板抄 Zone 2（60-70%），無視第二節把
走跑交替列在 50-60%。最嚴重的是 **Phase 1 的長跑本體就是走跑交替**，卻被標成 65-72%／RPE 5-6。

裁決依據不用我自己發明——原文第八節 `:175` 自己寫了操作順序：

> 4. 跑步日 → 對照第四節長跑進度表確認距離/時間,用第二節心率區間確認強度

所以：**第二節的項目類型對照表是強度的唯一真相來源**，模板那一欄只是粗標籤。

| 項目型態 | 心率 | RPE | 出處 |
|---|---|---|---|
| 恢復跑（原文另含走跑交替，第 12 條起課表裡沒有走跑） | 50-60% | 2-3 | 第二節 |
| Zone 2 有氧跑 | 60-70% | 4-5 | 第二節 |
| 長跑（全跑） | 65-72% | 5-6 | 第二節 |
| 節奏跑「稍快於 Zone 2」 | **70-75%** | 5-6 | **內插值**，標 `intensityDerived` |
| Marathon Pace | 75-80% | 6-7 | 第二節 |

Phase 1 的長跑：W1-6 現在是 Zone 2 跑 → 60-70%（**第 12 條**改的，原本是走跑交替 50-60%）；
W7-8 第四節寫「40分鐘 全跑」→ 才進 65-72%。
比賽日第二節沒有對應檔位，沿用「長跑」65-72%，並在 notes 寫明。

`verify_plan.py` 綁住這件事的斷言：「強度符合第二節對照表」「長跑強度：W1-6 60-70%、W7 起 65-72%」
「Phase 1 的 run 一律 60-70%」——後兩條是第 12 條時取代「走跑交替一律 50-60%」的。

## 7. 「A 或 B」是選擇題，不是「必做 + 可選的休息」

第一版把原文的「輕鬆跑 30分鐘 **或** 完全休息」編成「跑步（必做）+ 休息（optional）」，
等於把休息變成要額外勾選的加購，預設是做。**這直接違反第 0 條**——把負荷設成預設值。

改成 `day.selectOne = true`：兩個選項地位相等，UI 顯示成選擇題，完成任一即算完成。
全課表共 32 個二擇一日。`optional` 欄位整個移除，verify 有一條斷言擋它長回來。

## 8. 週跑量是參考上限，不是本週課表的加總（已被第 13 條取代）

第四節的「週跑量參考」欄被第一版升級成每週一個權威數字，但同一份 JSON 的 days 湊不到——
Phase 2 只有兩個跑步日，用原文自己的 8-9 分速換算，W13 是 15-17K 而欄位寫 22-25K。

**不自行補跑步日**（那會違反第 0 條：轉檔不該替使用者加量），改成標明性質：
`weeklyVolumeKm.kind = "reference"`，UI 顯示成「參考上限」。沒有數字的週寫明是哪一種
原文狀態（`weeklyVolumeNullReason`），不要讓 null 同時代表三件事。

> **2026-09-11 起作廢**：原文的參考欄整個不再進資料檔。使用者要「每週跑量目標 vs 實際」，
> 而一個照表練也達不到的參考上限拿來當目標，就是用數字催她加跑。現在目標由課表項目
> 即時加總，見第 13 條。`weeklyVolumeKm` 這個欄位名保留給教練模式的手動覆寫（只能往下調）。

原計畫的醫生放行前提（`:6`）、免責聲明（`:180`）、每週日自檢（`:176`）、

## 11. 教練模式：課表從「共用唯讀」改成「三人皆可寫」

原始規格書 `:23`「### 3.1 課表資料(共用、唯讀,所有人看到同一份)」與 `:16-17`
「不需要即時多人協作...各自打開自己的紀錄即可」，把課表定為所有人共用的一份唯讀資料。

使用者要求能直接在 UI 上調整訓練課程，不想每次都改 `tools/build_plan.py` 重新部署。
裁決：新增「教練模式」——mick/Annlin/Phoebe **三人都能切換進去編輯**，範圍「完全開放」
（新增/刪除/調整順序項目、切換二擇一、編輯週跑量），不限定某一人是「教練」角色。
這是對規格書 `:23` 的正面覆寫，不是遺漏：三人都是家人/訓練夥伴，沒有敵對關係，
沒有理由把編輯權限限定在一人身上。

**架構**：出廠課表（`data/plan.json`，git 版控）維持不變，教練模式的修改存進 Firestore
的 `planOverrides/{weekNumber}` 集合，疊加在出廠值上面（`Store.effectiveWeek()`）。
沒被改過的週繼續讀出廠值，改過的週優先讀 Firestore 那份。每週都能「還原成出廠預設值」。

**完成紀錄改成用項目 id 對應，不是陣列位置**——這是這個功能能安全存在的前提。
出廠課表的每個項目在 `build_plan.py` 的 `build()` 迴圈裡被賦予 `"{週次}-{星期}-{序號}"`
固定 id；教練新增的項目用 `crypto.randomUUID()`（前綴 `c-`）。`entries.done` 從
`itemsDone`（陣列，位置對應）換成 `{itemId: true}`（map，id 對應），`selectedChoice`
（索引）換成 `selectedItemId`（id）。如果沒有這個改動，教練調整順序或新增/刪除項目時，
舊的打勾紀錄會悄悄對到錯的項目上。

**這個決定引入的風險，跟已經補上的防線**（多代理審查抓到的，見 CHANGELOG v0.4.1）：

| 風險 | 防線 |
|---|---|
| 殘缺的覆寫文件讓所有人的畫面當機 | `Store._isValidWeekShape()` 存檔前擋、讀取時也擋，壞資料當作不存在退回出廠值 |
| 教練能刪掉二擇一日唯一的休息選項，變相強迫使用者失去休息（違反第 0 條） | `deleteItem` 擋下「刪除後不再有 rest 選項」與「selectOne 少於 2 個選項」 |
| 兩人幾乎同時編輯同一週，其中一人的修改靜默消失 | `pushPlanOverride` 用 Firestore transaction 比對版本，偵測到衝突就中止並提示重新整理 |
| 數值輸入沒有上下限，手滑打錯存進所有人共用的課表 | `saveItemEdit` 存檔前檢查時長/距離/RPE 的合理範圍 |

**反悔成本**：中等。拿掉教練模式＝拿掉 UI 入口跟 Firestore 規則的 `planOverrides` 段落，
`Store.effectiveWeek` 退化成永遠讀出廠值——出廠課表本身不受影響。已經寫進去的
`planOverrides` 文件可以留著不管（沒有 UI 讀取時就是死資料）或手動清空。

## 12. 課表裡沒有「走跑」：Phase 1 跑步日改 Zone 2 跑（強度 50-60% → 60-70%，使用者裁定）

使用者裁定（2026-09-11）：「不要有走跑的項目，應該是 Zone 2 跑，走跑太含糊。」

原文 Phase 1 的週二／週五跑步日與 W1-6 的長跑都是「走跑交替」（第二節:32，50-60%）。
現在整個拿掉：`walk-run` 這個類型從 `build_plan.py`、`verify_plan.py`、`views.js` 的
`VALID_TYPES` 全部移除，Phase 1 的跑步日改成 `run`「Zone 2 跑」60-70%，**時間數字完全不變**。

**這是負荷上升，要攤開講。** 第 1-8 週的週二／週五加第 1-6 週的週六，共 21 個未過期的日子，
心率從 50-60% 變 60-70%、RPE 從 2-3 變 4-5。第 0 條的驗收句（「之後某一天的負荷會不會比原本高？」）
對這次改動的答案是「會」——但第 0 條管的是**休息或受傷的調整**不能變相加量，這次是使用者
對自己課表的正面裁定，且她用的字眼就是「Zone 2」（第二節明確的 60-70% 那一檔）。
記在這裡的用意是：這是她知情的決定，不是轉檔順手帶過的加量。Phase 1 跑步項目的 notes
補上原文第 28 行的「Zone 2 上限先抓保守一點」與講話測試（她沒有最大心率數據）。

**W1-6 的長跑用 60-70%，不是 65-72%。** 它現在的 type 是 `long-run`，第二節「長跑」的
慣用強度是 65-72%——但原本是 50-60% 的走跑，改成 Zone 2 跑只該進一級，順手標成長跑強度
等於連跳兩級。W7-8 原文寫「40分鐘 全跑」才進 65-72%。`verify_plan.py` 的
「長跑強度：W1-6 60-70%、W7 起 65-72%」與「Phase 1 的 run 一律 60-70%」兩條斷言綁住這條，
第 6 條的「走跑交替一律 50-60%」斷言隨走跑一起移除（第 6 條本文已同步改）。

**已存在的教練覆寫**：教練模式在這之前改過的週，覆寫文件裡可能還有 `walk-run` 項目。
它們照常顯示（標「走跑交替（舊類型，請改選）」），算跑量時視同 `run`；教練點編輯時必須改選
類型才能存檔，不會被靜默換成別的類型。覆寫文件從此記 `basePlanVersion`，低於出廠版本時
教練面板顯示「這週的調整基於舊版」並指向「還原本週」。

**反悔成本**：低。改回走跑是 `build_plan.py` 的模板改回去、`VALID_TYPES` 加回一個字串、
重跑產生器。已經在 Firestore 的完成紀錄用項目 id 對應，id 沒變，舊紀錄不受影響。

## 13. 舊 Notion 課表格式的整合：每日「實際操作」、四態狀態、週跑量目標 vs 實際、訓練目標

使用者的前一份訓練計畫（Notion，三鐵）用了 15 週的表格，穩定的核心是四欄：
星期｜訓練內容｜重點／強度｜**實際操作（完成度）**。她實際在最後一欄寫的是四種東西混在一起：
狀態（完成／錯過／休息）、替代（「改肌力訓練」「受傷 改 單車」）、實際數字、身體感受。
這條把那個格式拆進現在的資料模型，並加上使用者另外要的「每週跑量目標與實際」和「可以設定訓練目標」。

### 13a. 每天一個「實際操作」方塊（`entries.actualNote`、實際分鐘／公里搬到這裡）

- `actualNote`：自由文字，跟打勾同一份文件、白名單三人可讀（Notion 那欄本來就是給教練看的）。
  身體狀況仍寫 `private.note`（第 2 條不動）。兩個文字框並排、**標題直接寫誰看得到**
  （「Annlin、Phoebe 看得到」／「🔒 只有你看得到」），私密欄從收合改成預設展開——
  提示文字不是防線，兩個框都看得到才會分流。
- 實際分鐘／公里本來就是一天一筆（`entries.actualDurationMinutes / actualDistanceKm`），
  之前畫在每張項目卡上，一天兩個有時長的項目就是兩個輸入框綁同一個值。現在只畫在這個方塊。
  公里欄在當天有跑步類項目、或狀態是「改做」時顯示（改做成跑步也要能記公里）；
  「錯過」「主動休息」時不顯示、且數字清成 null。

### 13b. 一天的狀態：打勾推導 + 三個覆寫值（`entries.status`）

`status` 只有 `null`（照表，由打勾推導 done/partial/pending）、`substituted`（改做）、
`missed`（錯過）、`rested`（主動休息）四種。**沒有 `done`**——完成永遠靠打勾，不另存一個
會跟打勾矛盾的欄位。打勾跟覆寫互斥、由 `Store` 維護：打勾＝清掉 status；設覆寫＝清掉勾。
「照表」不是一顆可以按的 chip，是方塊右上角的唯讀文字（「照表 · 部分完成」）。

完成率（「照表完成率」）的分母：拿掉過期日、課表本身全休息的日子、`rested`、**以及 `substituted`**。
改做是第 0 條唯一允許的補做方式（「取代，不疊加」），把它算成跟錯過同分會把人推向硬照表操課。
`missed` 留在分母、不進分子。不另算「有練率」——多一個分數就多一個催人的數字。
純休息日不放狀態 chip（在休息日給「改做」按鈕＝App 主動遞出「用訓練取代休息」）；
未來的日子只能預先排「主動休息」。

### 13c. 週跑量目標 vs 實際（取代第 8 條）

目標**不存進 `plan.json`**，由 `Store.weekTargetAuto` 從該週的跑步項目即時加總——教練改了
項目，目標自動跟著變，不會有兩個必須互相對應的數字。規則：

- 只算 `run / long-run / tempo`（＋舊的 `walk-run`）；`race` 不算——比賽是終點不是那週的跑量，
  算進去賽週目標 47K+，26 週的圖被那一根壓扁。賽週卡片另外一行「週日比賽 42.195 km 另計」。
- 只有時長的項目（Phase 1 全部）用 `plan.timeBasedRunPaceMinPerKm` 換算，**取原文 8-9 分速的慢端 9**：
  公里＝分鐘÷分速，分速數字越小目標越高，要低估就取慢端（第一版寫 8 還註解成「偏低」，方向反了，
  W7-8 算出 10-11.9K 超過原文自己的 8-10K 參考上限）。`verify_plan.py` 守 `≥ 9`。UI 標「約」。
- 過期日、使用者標 `rested` 的日子、`substituted` 且沒記公里的日子（改騎車、改核心）不算——跟完成率的分母
  同一套（第 0 條：降量週縮小分母）。`substituted` 有記公里（改做的也是跑步）就照算，跟實際對得上。
  `missed` 照算，缺口是真的。
- 二擇一的日子：下限取各選項最小值（休息＝0，所以含休息的日子下限自然不含它）、上限取最大值。
- 實際＝各天公里加總；照表的日子沒填公里但有填分鐘、且當天有跑步項目 → 用同一個分速換算
  （跟目標對稱，否則 Phase 1 八週的實際永遠是「—」），標「約」。改做的分鐘不換算（不知道是不是跑步）。
- 已標記「本週降量」的週：不畫進度條、不比對，只顯示實際（原定目標放在括號裡）。
- 進度條的 100% 點是目標**下限**（碰到下限就滿格）；超過上限改顯示警示文字「已超過本週課表上限——下週不要再加」，
  不畫「多出來」。填滿型的條會催人往上限跑。

**教練模式可以手動設定週目標**（使用者要求「可以設定訓練目標」），但**上限不能高於課表加總**——
數字只能把目標調低。要加量請改課表項目，那才看得見、也才會被審。留空＝改回自動加總。

### 13d. 訓練目標（`users/{userId}/profile/goals`，每人各自）

比賽目標一句＋自訂目標清單（文字＋達成勾）。白名單可讀（一起練的人看得到）、只有本人可寫。
**目標只收文字、不畫進度、不跟週跑量卡連動**——否則它會變成使用者自己給自己加的第二支進度條。
Notion 的「總目標」（VO₂max 34 → 40）與「檢查點任務」都可以寫成一條條文字。

### 13e. 週視圖加「表格」模式

三欄「日｜課表｜實際」並排，模仿 Notion 表格給回顧用；卡片模式維持原樣給手機打勾用。
切換用本機 localStorage 記住（跟主題、教練模式同一類裝置偏好）。

### 順帶修掉的既有問題

- `firebase-sync.js` 綁 `Store._cloudPushPlanOverride` 時少接了第三個參數 `baseUpdatedAt`，
  版本比對永遠拿到 `undefined`，同一週第二次教練編輯必定被判成「剛被別人改過」而丟掉；
  `_cloudDeletePlanOverride` 同樣少接 `backup`，還原失敗永遠不回滾。改用 `bind`，參數數量不可能再對不上。
- 遠端文件寫回本機從「整份 last-write-wins」改成「逐欄位合併」（`mergeDocs`）：雲端是 `set(merge:true)`
  逐欄位合併，但 `updatedAt` 整份一個——兩台裝置分別改同一天的不同欄位時，舊做法兩台各只看到自己的欄位，
  且永遠不會自我修正。
- 總覽頁在未登入時就訂閱別人的 entries，訂閱失敗後仍被記成「已訂閱」，登入後不再重訂——現在未登入不訂閱。
- `_writeOwnEntry` 對 `undefined` 欄位直接丟例外（可執行守衛，不是註解）：`undefined` 會讓本機清掉欄位、
  雲端卻保留。

**反悔成本**：低到中。狀態與 actualNote 是純加法欄位，舊文件缺 key 讀成 null；拿掉功能只是拿掉 UI，
資料留著無害。週跑量改回存數字則要回到第 8 條的兩個真相來源問題，不建議。

## 14. 環境因素讓某天跟另一天對調：個人、單週的「顯示順序」，不是課表內容改變

使用者的情境：這禮拜因為環境因素，週一跟週三的內容要對調（例如場地/天氣讓她今天只能做
原本排週三的內容）。討論過三個方向（整天對調／單一項目搬到別天／拿掉「哪一天」這個
限制改成本週待辦清單），選了**整天對調**：

- 它精準對應「對調」這個情境，其餘兩個方向要嘛沒對到（清單模式）、要嘛有風險（單一項目
  搬到別天可能讓某天疊兩份課，是第 0 條要防的「補做疊在既有課表上」）。
- 它是一個**排列**（permutation）：七天的內容一個不多一個不少，第 0 條的驗收句
  「會不會變相加量」直接答「不會」——這是唯一不需要額外防呆規則就通過的方案。

**資料模型**：`weekAdjustments/{weekNumber}`（跟「本週已降量」同一份文件、同一套可見性——
白名單可讀，只有本人可寫）多一個欄位 `dayOrder`：長度 7、涵蓋 0-6 的排列，
`dayOrder[i]` = 日曆上第 i 天（週一=0）實際顯示出廠課表第幾天的內容。預設（欄位不存在或
不合法）當作 identity `[0,1,2,3,4,5,6]`。**課表項目本身完全不動**，只是換一個標籤讀。

**日期歸屬不變、內容歸屬換**：`entries` 仍然用日曆日期 + 項目 id 對應（沒有新欄位）——
「哪天做的」看日期，「做了什麼」看項目 id，兩者本來就是分開存的，對調只是改變「這個日曆
格子該顯示哪個出廠天的項目清單」，完成紀錄的儲存方式完全不用變。這是當初教練模式把
項目 id 做成固定值時順便換來的（決策紀錄第 11 條）。

**教練模式一律忽略對調**：`Store.effectiveDayOrder` 在 `coachMode` 開著時永遠回傳 identity。
理由：教練模式編輯的是所有人共用的課表結構，且畫面上「日曆格子」跟「要編輯的出廠天」
是同一個 dayIndex（`renderDayDetail` 的教練工具列、`_cloneEffectiveWeek` 都是這樣用的）——
如果對調在教練模式下也生效，會編輯到錯的一天。這也代表個人對調的 UI（週視圖的「本週
順序」卡片）在教練模式開著時不顯示，因為顯示了也不會生效，只會讓人以為壞了。

**跨人看進度也要拿得到對方的對調**：總覽頁「查看別人的進度」算完成率／週跑量時，
如果不知道對方自己的 `dayOrder`，會拿錯的內容去對他的打勾紀錄（他打勾當下看到的是
他自己對調後的畫面）。所以 `weekAdjustments` 的 Store 快取從「只存自己」改成
`{ [userId]: {...} }`（跟 `entries` 同一個形狀），並新增 `Sync.subscribeOtherWeekAdjustments`，
跟既有的 `subscribeOtherEntries`／`subscribeOtherProfile` 同一套。

**反悔成本**：低。拿掉功能＝ `effectiveDayOrder` 永遠回傳 identity，UI 拿掉「本週順序」卡片；
已經存在的 `dayOrder` 欄位是死資料，不影響任何計算。

## 15. 教練模式下可以互相設定訓練目標，不限定某一人是教練

使用者（mick）提出：「我是教練，我要給 Annlin 跟 Phoebe 設目標」。

裁決：**沿用第 11 條教練模式已經定案的哲學**——「三人都是家人/訓練夥伴，沒有敵對關係，
沒有理由把編輯權限限定在一人身上」。所以不是「只有 mick 能設別人的目標」，而是
**教練模式開著時，白名單內任何人都能編輯任何人的訓練目標**，跟教練模式改課表內容
用同一顆開關、同一套精神。程式碼裡完全不出現 mick 這個特定身分——避免把一次性的
使用情境寫死成程式邏輯，之後角色互換（例如 Phoebe 也想幫 mick 設配速目標）不用改碼。

**規則層**：`firestore.rules` 的 `users/{userId}/profile/{doc}` 寫入權限從
`isSelf(userId)` 放寬成 `isMember()`——跟 `planOverrides` 同一個模式（規則層不知道
「教練模式」這個 UI 開關是不是開著，那是體驗層的守門，不是安全邊界；真正擋住的是
白名單本身）。這個集合目前只放 `profile/goals`，不放身體狀況等敏感資料——那些走
`private/` 子集合，權限沒有變。

**程式層**：`Store` 的目標寫入函式（`setRaceGoal`/`addGoal`/`toggleGoalDone`/`setGoalText`/
`removeGoal`）都加一個可選的 `targetUserId`，不傳＝寫自己的（維持原本行為，向後相容）。
教練幫別人寫的目標**只留在記憶體**（靠既有的 `subscribeOtherProfile` 保持最新），
不寫進教練自己裝置的 localStorage 快取——那是別人的資料，不該用自己的裝置快取它。
`renderGoalsCard` 的可編輯條件從「只有自己」改成「自己，或教練模式開著」；後者顯示
「教練模式編輯」標籤，避免看起來像目標是自己的。

**目標本身的邊界沒有變**（決策紀錄原文第 13d 條）：只收文字、不畫進度、不跟週跑量卡
連動，也不會改變任何一天的課表內容——這條裁決只放寬「誰能寫」，不放寬「目標能做什麼」。

**反悔成本**：低。改回「只有本人能寫」＝ rules 的 `profile` 寫入改回 `isSelf(userId)`、
`renderGoalsCard` 的 `editable` 條件拿掉 `|| Store.coachMode`。已經被教練寫入的目標
資料本身沒有格式差異，不需要遷移。

## 16. 登入流程以 babylog 為準，不做任何瀏覽器／裝置判斷

登入問題回報了三次（v0.4.2、v0.6.1、v0.6.2 各修一次），三次修法全部是錯的方向，
最後一次（v0.6.2）更是把原本能用的「加入主畫面」模式整個擋掉：

| 版本 | 假設 | 實際 |
|---|---|---|
| v0.4.2 | Safari 的 ITP 擋掉 popup 的回傳 → Safari 改用 `signInWithRedirect` | 方向相反。Firebase 自己的文件寫明：在會擋第三方資料的瀏覽器上，redirect 導回來會拿到空使用者，**建議的做法是用 popup** |
| v0.6.1 | UA 判斷漏掉 iOS 上的 Chrome/Firefox（也是 WebKit）→ iOS/Firefox 一律 redirect | 把 v0.4.2 的錯誤方向擴大到更多瀏覽器，Safari 分頁也登不進去了 |
| v0.6.2 | 「加入主畫面」是嵌入式 webview，Google 封鎖、儲存空間隔離 → 直接不讓登入 | **錯**。babylog 與日文學習 App 同一套架構（GitHub Pages + firebaseapp.com authDomain + compat SDK 12.17.0）在主畫面模式登入、同步都正常。網路搜尋到的「webview 被封鎖」講的是原生 App 內嵌的 WKWebView，不是 Safari 的主畫面網頁應用程式 |

裁決：**登入流程一字不差照抄 babylog 的 `signInWithGoogle()`**——`signInWithPopup` 優先，
只有 `auth/popup-blocked` 才退回 `signInWithRedirect`，`auth/popup-closed-by-user` 回 idle，
其餘顯示失敗。不做瀏覽器 UA 判斷、不做 `navigator.standalone` 判斷、不做逾時計時。
順便把 babylog 2026-08-02 事故的 `experimentalAutoDetectLongPolling` 也帶進來（同一支手機、
同樣的行動網路，串流連線被中間設備弄斷時自動退回 long-polling）。

兩個保留的、跟 babylog 不同的小改動（都只是讓失敗看得見，不改變登入機制）：
- `renderSyncPill()` 在「沒登入」的區塊也判斷 `signing-in`／`fail`／`unauthorized`——
  之前這些狀態排在「沒登入 → 點擊登入以同步」之後，永遠顯示不出來。
- `_handleSnapErr` 判定未授權後 `signOut()`，`onAuthStateChanged` 的 null 分支**保留**
  `unauthorized` 狀態並在訊息裡寫出被拒絕的 email（babylog 也這樣做）——不然畫面會退回
  「點擊登入以同步」，使用者看到的是「登入完全沒發生」，而不是真正的原因（帳號不在
  白名單／`firestore.rules.local` 改了沒發布）。

**這次的教訓（記在 memory，供所有專案）**：手上有同一套架構、確定能用的先例
（babylog）時，**先逐行比對先例，不要用網路搜尋的結果推翻先例**。三次修法都是「搜尋
→ 找到一個聽起來合理的成因 → 改」，沒有一次先去看 babylog 到底怎麼寫的；而 babylog
的程式碼從第一天就擺在那裡。搜尋結果描述的是「某些情境下會發生的事」，先例證明的是
「這個情境下不會發生」，後者的證據強度高得多。

**反悔成本**：無——這是回到已經驗證過的做法。

## 17. 拿掉「今日」頁：本週頁改手風琴；新增「改做類型」與「體感強度」兩個紀錄欄位

使用者要求（2026-09-12）：刪掉今日頁，想保留的內容搬到本週頁、改成手風琴展開；
實際操作加「改做了什麼」的快速選項；新增 Apple Fitness「Rate Your Effort」式的體感強度；
身體狀況收合；安全提醒收進「！」；跑量說明收進「？」；底部被導覽列遮住要修。

**手風琴**：本週頁七列各自可展開，一次只開一列，展開的列身就是原本今日頁的內容
（訓練說明 → 實際操作 → 身體狀況）。開 App、按「本週」、切到今天那一週時，**今天那一列
自動展開並捲到可見**——「打開就看到今天」這件事保留，只是不再是獨立一頁。導覽列變三格。
表格模式（課表｜實際）留著當回顧用。

**改做類型（`entries.substituteType`）**：點了「改做」才出現第二排——跑步｜重訓｜核心｜
騎車｜游泳｜走路｜其他。兩下點完，不用打字。週跑量規則跟著變準：**只有改做「跑步」的
公里才算**（之前是「改做＋有填公里就算」，改騎車填 20 km 也會被加進跑量，不對）；
改成非跑步類時公里欄不顯示、已填的公里清掉。沒選類型的舊紀錄維持舊規則。

**體感強度（`entries.effort`，1-10）**：這是「實際」，跟課表項目的 `rpe`（「要求」）分開存。
UI 照 Apple 的四階梯：1-3 輕鬆、4-6 中等、7-8 困難、9-10 全力，十個點點哪個就是幾分，
再點一次清掉。課表要求的 RPE 區間在階梯上用淡色點標出（二擇一取選中的那個項目）。
**只有「打得比課表高」才提示**（「比課表要求吃力——隔天看狀況」）——第 0 條：實際比要求
吃力是要留意的訊號，不是反過來要往上打；打得低什麼都不說。錯過／主動休息的日子清掉、
不顯示（沒東西可評）。

**身體狀況**：三顆旗標常駐一排；備註框有旗標、有內容、或點「＋備註」才展開。「只有你
看得到」標籤常駐——分流靠標題，不靠 placeholder（第 13a 條的原則不變）。

**安全提醒**：本週頁標題旁一顆「！」，點了開全文彈窗。第 10 條的四段文字**可以藏，
不能少**——`verify_plan.py` 只驗 `plan.json`，畫面這邊靠 `renderModal` 自己守四段都在。

**底部留白**：`#root` 的 `padding-bottom` 從寫死 84px 改成 `calc(84px + env(safe-area-inset-bottom))`
——主畫面模式下 iPhone 的 home indicator 安全區會完整算進導覽列高度，之前差十幾到二十幾 px。

**還沒做（第二批）**：拖曳換順序取代「本週順序」卡片（要接觸控，用 SortableJS）；週日回顧
統計「這週幾天比課表吃力」。

**反悔成本**：低。兩個新欄位是純加法（舊文件缺 key 讀成 null）；手風琴是純顯示層，
`renderDayBody` 就是原本的 `renderDayDetail` 去掉標頭。

## 18. 本週順序改成拖曳；「本週順序」卡片拿掉

第 17 條的第二批（2026-09-12）：「刪除切換順序欄，改成手動拖曳互動式切換」。

**做法**：每列右邊一顆 ⋮⋮ 把手，按住拖到想要的位置放開。**插入語意**（把第 from 格
拿出來插到第 to 格，中間順移一格），跟 iOS 清單拖曳一樣——不是「兩格對調」。
資料層還是第 14 條那個 `dayOrder` 排列，只是入口從兩個下拉選單變成 `Store.moveWeekDay`；
拖回出廠順序時一樣清掉 `dayOrder` 不留空紀錄。`swapWeekDays` 刪了（沒有第二個入口）。

**用 SortableJS（cdnjs）不自己寫**：觸控拖曳要處理長按判定、跟捲頁打架、自動捲動、
放開時的動畫——這些都是別人踩過幾百次的坑。設 `delay:150, delayOnTouchOnly:true`
（手指按住一下才開始拖，短按照常展開那一列）、`forceFallback:true`（桌機手機同一套，
不靠瀏覽器原生 DnD，iOS Safari 的原生 DnD 行為不一致）。**沒載到就退化**：`views.js`
不畫把手、`app.js` 不掛，其他功能不受影響；「還原順序」不靠它——所以離線或 CDN 被擋
只是不能拖，不是壞掉。

**每次重繪重新掛**：`render()` 整個換掉 `#root`，所以 `main.js` 畫完呼叫 `App.afterRender()`
在新 DOM 上重掛。`onEnd` 裡用 `setTimeout(…,0)` 再重繪，不在 Sortable 還握著節點時把
DOM 換掉。展開的那一列跟著內容走（被拖的就是它 → 落點；在拖動範圍內的 → 順移一格）。

**留下的**：一行提示「按住 ⋮⋮ 拖曳可換這週的順序」；對調過之後變成「已對調：週一顯示
週三的內容」＋「還原順序」。表格模式跟教練模式不能拖（教練模式下 `effectiveDayOrder`
一律回出廠順序，第 14 條）。

**順手加的**：週日回顧多一行「這週有 N 天體感比課表要求吃力——下週照表，不要加」
（第 17 條的 `effort` 對項目 `rpe.max`）。只提醒不要加，不會建議補——第 0 條。

**反悔成本**：低。資料格式沒動；把 SortableJS 拿掉就是回到沒有拖曳的畫面。
