# 決策紀錄

規格審查（2026-09-10）留下的待決事項，在這裡定案。每一條都寫了「為什麼這樣選」與「反悔的成本」，
之後想改的時候不用重新推導一次。

---

## 0. 最高原則（使用者訂的，覆蓋以下所有細節）

> **休息或受傷的調整，不應該變相增加強度。**

這條不是感想，是可以拿來裁決設計的規則。它直接推翻三種常見做法：

| 常見做法 | 為什麼違反 | 本專案怎麼做 |
|---|---|---|
| 這週降量了，把少掉的量加到下週 | 把休息的代價往後推，等於沒休息 | 降量週**縮小分母**，少掉的量就是少掉了，不補 |
| 漏掉的課排進「補做清單」，累積起來 | 補做疊在既有課表上＝那天變成雙倍 | 補做只能**取代**當天原本的內容，不能疊加 |
| 中斷兩週回來，把剩下的週數壓縮 | 同樣的總量塞進更少的週＝強度上升 | 中斷就是往後順延，或直接接受計畫縮短 |

**驗收方式**：任何一個「調整」功能寫完之後，問一句「使用者用了這個功能，之後某一天的負荷會不會比原本高？」
會，就是做錯了。

## 1. 儲存後端 → **Firebase Auth + Firestore**

規格書原本寫「GitHub Contents API」，但那是 babylog **已經廢棄**的架構
（`~/Documents/Projects/babylog/docs/sync.md:4`：「已經整個換掉」）。廢棄理由（同檔 `:10`）：

> GitHub 版本每支手機都要手動申請、貼上一組 GitHub token 才能同步，對非工程背景的家人不友善。

而這個 App 的分享對象正是伴侶與教練。同一個坑不踩第二次。

**這個決定同時解掉四個問題**：blob sha 衝突、離線佇列、寫入權限強制、身分驗證。
Firestore 一天一筆文件（`users/{userId}/entries/{date}`）天生就是文件級併發，兩台裝置改不同天不會互相覆蓋。

**反悔成本**：低。Firebase 專案可以刪掉重來，資料量小。

## 2. 敏感健康資料的可見範圍 → **預設完全不分享**

`flags`（漏尿／疼痛／過度疲勞）與 `note`（自由文字身體狀況）**不進共享路徑**。
總覽頁看別人的完成度時，只讀 `status` 與時長的聚合結果，讀不到 flags。

Firestore 路徑分層：

```
users/{userId}/entries/{date}      ← status / 實際時長 / 距離   （白名單內可讀）
users/{userId}/private/{date}      ← flags / note              （只有本人可讀）
```

Security Rules 裡 `private/` 子集合綁 `request.auth.uid == userId`，不是靠前端不顯示。
babylog `docs/sync.md:23`：「真正的防線一定是 Security Rules，前端檢查只是體驗優化。」

**為什麼不問你**：分享是隨時可以打開的，收回來很難。預設關閉、之後想開再開。

## 3. Phase 1 的週四 → **改成產後專門課程，不用 Pamela Reif**

原始計畫自己就寫了（`docs/計畫原文/訓練計畫.md` 第六節）：

> **Pamela Reif 本身沒有針對「產後/骨盆底」設計的專門系列**

以及「已確認產後恢復良好、醫生已放行一般運動強度」的階段「(通常 Phase 2 之後)」才適合直接用她的影片。
但 Phase 1 模板卻把 Pamela 排進 Week 1-8 的每個週四——同一份文件的正面衝突，
而且衝突方向朝著**安全性較差**的一邊。

裁決：第六節的安全性說明優先於模板。Phase 1 週四改成產後骨盆底/腹直肌專門課程
（原計畫點名的 Fitness Blender *Postpartum Core and Pelvic Floor Recovery Series*），
依規格書 `:93` 的規則**只留搜尋關鍵字、不生成 URL**。Phase 2 起才換成 Pamela Reif。

**反悔成本**：低，改一個 `videoRef`。但反過來（先用了 Pamela 才發現不該用）成本在身體上。

## 4. Week 23-26 的 28 天 → **從第四節進度表推導，並標記為推導值**

原始計畫只有 Phase 1/2/3 三張每週模板；Phase 4 只有三條 bullet，賽週完全沒有每日內容。
但第四節的長跑進度表有這四週的資料（W23 20K、W24 12K、W25 8K、W26 3-5K 喚醒跑）。

裁決：用 Phase 3 的每週結構 + 第四節的量，推導出這 28 天，每一筆標 `"derived": true`，
App 上顯示成「推導值，可調整」。**不留 28 天空白**（那會讓 App 在最重要的四週變成空的），
也**不讓 AI 自由發揮**（標記讓你一眼看出哪些不是原文寫的）。

順帶解掉兩個計畫內部矛盾：
- Phase 4 長跑數列，模板寫「12K → 8K → 5K」但第四節寫「20K / 12K / 8K」——**以第四節為準**，5K 歸還給賽週。
- Phase 3 長跑上限三處寫三個數字（26-30K / 28-30K / 26-28K）——**取 28K**，依計畫自己的定位「安全完賽+良好體驗」。

## 5. 起算日改 2026-09-07 之後的前三天 → **標記為已過期，不要求補做**

起算日從 `2026-09-10`（週四）改成 `2026-09-07`（週一），26 週才剛好 182 天整、
且比賽日落在第 26 週最後一天。副作用是今天（9/10）一打開 App 就已經在第 1 週第 4 天，
9/07–9/09 三天成了過去式。

裁決：這三天標 `expired`，**不計入完成率分母，也不提示補做**。

理由直接引第 0 條：要求補做 = 第一週就比原本多三天的量。開場就違反最高原則的設計不能留。
