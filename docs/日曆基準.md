# 日曆基準

**這份是課表日期的單一真相來源。** 任何地方需要「第 N 週是哪幾天」都以此為準，不要各自算。

- 起算日 `startDate` = **2026-09-07（週一）**
- 比賽日 `raceDate` = **2027-03-07（週日）**
- 總長度 = **182 天 = 26 週整**，比賽日落在第 26 週第 7 天

推導公式（App 端只存 `startDate` + `weekNumber` + `dayIndex`，其餘全部算出來）：

```
date       = startDate + (weekNumber - 1) × 7 + dayIndex        // dayIndex 0-6
dayOfWeek  = 「一二三四五六日」[dayIndex]                          // 不存進資料檔
```

> ⚠️ **不要把 `date` 或 `dayOfWeek` 寫進課表 JSON。** 原規格書兩者都存，結果第一筆
> `"date": "2026-09-10"` 配 `"dayOfWeek": "一"` 就已經對不上（那天是週四）。
> 兩個必須互相對應的數字＝缺少單一真相來源。

## 長跑數字的取捨

原始計畫在三處給了不一樣的數字，以下為裁決結果（詳見決策紀錄第 4 條）：

- **Phase 3 上限取 28K**（原文另有 26-30K 與 28-30K 兩種寫法）
- **Phase 4 取第四節進度表的 20K / 12K / 8K**（原文模板另寫 12K → 8K → 5K）
- **5K 歸還給賽週**的喚醒跑，不在 Phase 4 重複出現

## 驗證

`tools/verify_plan.py`（CP1 一併產出）會對課表 JSON 跑以下斷言，之後每次調整課表都要重跑：

1. 攤平後是連續日期，無缺無重，總數 = 182
2. 每個 week 剛好 7 天，第一天的 `dayIndex` 為 0
3. `phases` 的 weekRange 互不重疊、無空洞、涵蓋 W1-26
4. 每個非 null 的 `videoRef` / `workoutRef` 都能在對應清單找到
5. `raceDate` 等於最後一天
6. 資料檔裡**不存在** `date` 與 `dayOfWeek` 欄位（防止衍生欄位偷偷長回來）
